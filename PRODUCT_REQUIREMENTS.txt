SR ENTERPRISES CRM — PRODUCT & ENGINEERING REQUIREMENTS
==========================================================

Document Type:
    Master Product Requirements / Engineering Requirements

Purpose:
    This file is the single high-level requirements reference for building
    the SR Enterprises CRM. It defines product scope, architecture,
    functionality, UX, security, data relationships, integrations,
    performance, deployment, and quality requirements.

IMPORTANT:
    This is NOT a Python dependency file. The project is TypeScript/Node.js
    based. JavaScript/TypeScript dependencies must be maintained separately
    in package.json / package-lock.json.

==========================================================
1. PRODUCT IDENTITY
==========================================================

Product Name:
    SR Enterprises CRM

Business:
    RO water purifier sales, spare-parts sales, RO repair and home-service
    business.

Primary Product Type:
    Deployed, web-first CRM with Progressive Web App (PWA) installation.

Desktop Experience:
    The CRM must be installable from supported browsers such as Chrome/Edge
    through the browser's native PWA installation experience. After
    installation it should open in an app-like window.

Primary Deployment Model:
    Cloud/deployed application.

Connectivity:
    Online-first. Internet is required for server-backed operations.
    The application should gracefully detect and communicate connectivity
    status.

3. DESIGN PRINCIPLES
==========================================================

The product must:
    - Feel like a professionally designed commercial SaaS.
    - Never look like a generic AI-generated dashboard.
    - Prioritize clarity over information density.
    - Use consistent spacing, typography, icons, components and interaction
      patterns.
    - Be fast and responsive.
    - Be usable on desktop, tablet and mobile.
    - Avoid unnecessary modules and navigation items.
    - Keep the sidebar consistent across all pages.
    - Avoid visual clutter.
    - Use meaningful empty states, loading states and error states.
    - Use smooth, purposeful animations only.
    - Never sacrifice usability for visual effects.

Theme:
    - Main application background: white / very light neutral.
    - Primary dark brand/navy color family.
    - Primary brand accent: blue.
    - Secondary accents may be used for status communication.
    - Accent colors must be restrained and consistent.
    - Avoid excessive gradients and excessive colors.
    - Sidebar design must remain visually consistent across every page.

Sidebar:
    Main options:
        Dashboard
        Customers
        Sales
        Invoices
        Services
        Inquiries
        Analytics
        Warranty
        Technicians
        Notifications
        Settings

    Sidebar requirements:
        - Same design across all pages.
        - Icons must be consistent.
        - Active page must be clearly highlighted.
        - Sidebar must support responsive behavior.
        - Tooltips should identify icons where labels are hidden.
        - Do not add unrelated ERP modules.

Explicitly excluded from main navigation:
    Reports
    Quotations
    Suppliers
    Purchases
    Inventory
    Payroll
    HR
    Marketing Automation

==========================================================
4. SINGLE SOURCE OF TRUTH
==========================================================

PostgreSQL is the authoritative business-data source.

The same business entity must never be duplicated unnecessarily.

Core principle:
    Enter data once -> derive and reuse it everywhere.

Example:
    Sale
      -> Customer Asset
      -> Invoice
      -> Warranty
      -> Service Schedule
      -> Customer Activity
      -> Analytics

A customer profile must aggregate related business records rather than
maintaining duplicate copies.

12. SERVICE HEATMAP
==========================================================

The service heatmap is mandatory.

Visual reference:
    GitHub-style contribution/activity heatmap.

Requirements:
    - Square cells.
    - Activity intensity represented by cell intensity.
    - Clear legend from low to high activity.
    - Current day highlighted distinctly.
    - Selected date/range clearly indicated.
    - Clicking a cell displays services for that date.
    - Services appear below/alongside the heatmap.
    - Heatmap data must be generated from actual service schedules.
    - No mock/static heatmap data in production.

Time filters:
    Year
    Month
    Week
    Day

Current period highlighting:
    - Day mode: current day highlighted.
    - Week mode: current week highlighted.
    - Month mode: current month highlighted.
    - Year mode: current year highlighted.

Clicking a heatmap period must filter the service list.

Service list details should include:
    Service ID
    Customer
    Phone
    Address
    Machine/asset
    Service type
    Warranty/general classification
    Technician
    Scheduled date
    Scheduled time
    Status
    Job card
    Relevant notes

==========================================================
13. WARRANTY SERVICES
==========================================================

Warranty services are automatically generated from product warranty data.

Example:
    Machine warranty = 2 years
    Service interval = 6 months

System generates:
    Service 1
    Service 2
    Service 3
    Service 4

The service schedule must immediately appear in the heatmap.

Warranty service status must automatically change when warranty expires.

Rule:
    If service is within active warranty coverage:
        Warranty Service

    If warranty has expired:
        General Service

The system must not require manual reclassification.

==========================================================
14. GENERAL SERVICES
==========================================================

General service is created when a technician recommends a future service.

Example:
    Technician completes service.
    Technician recommends next service after 2 months.
    User schedules next service.
    Service appears in upcoming services and heatmap.

Do not create future general-service records unless the user/technician
actually schedules the next service.

==========================================================
18. SPARE PART WARRANTY
==========================================================

Spare parts must have their own warranty lifecycle.

Example:
    Spare warranty = 6 months

If defective within warranty:
    Customer receives free replacement.

If warranty expired:
    Customer must purchase replacement.

Warranty validation must be automatic.

At shop/service interaction:
    Search customer
    Select spare-part asset
    Check warranty status
    If active -> replacement eligible
    If expired -> paid replacement

Replacement must be recorded in customer history.

27. AUTHENTICATION & SECURITY
==========================================================

Login:
    Username
    Pre-set password
    CRM-generated CAPTCHA

CAPTCHA:
    - Generated by backend.
    - Short-lived.
    - Server validated.
    - Invalidated after use.
    - Regenerated after failed authentication where appropriate.

Login protection:
    Maximum 3 failed attempts.
    Server-side rate limiting.
    Temporary lockout after limit.
    Refreshing browser must not reset attempts.

Passwords:
    Argon2id hashing.
    Never store plaintext passwords.

Sessions:
    Secure HTTP-only cookies.
    Secure flag in production.
    SameSite configured appropriately.
    Session expiry.
    Logout invalidation.
    Optional inactivity lock.

Secrets:
    Never store API secrets in frontend code.
    Never expose service credentials to browser JavaScript.
    Never store secrets in localStorage.

45. DEVELOPMENT RULES FOR ANTIGRAVITY
==========================================================

Antigravity must:

    - Treat this file as the master requirements reference.
    - Never invent new modules without explicit approval.
    - Never remove an approved requirement.
    - Never replace the chosen technology stack without approval.
    - Never introduce Laravel.
    - Never introduce PHP.
    - Never introduce Firebase as the primary backend.
    - Never introduce Supabase as the primary backend.
    - Never use SQLite as the production source of truth.
    - Never use mock data in production workflows.
    - Never hardcode business analytics.
    - Never put secrets in frontend code.
    - Never bypass backend authorization.
    - Never directly access PostgreSQL from React.
    - Never duplicate source-of-truth customer/sale/service data.
    - Preserve existing UI/UX decisions when implementing new functionality.
    - Use reusable components.
    - Use typed interfaces/schemas.
    - Add tests for important business logic.
    - Keep accessibility in mind.
    - Keep responsive behavior intact.
    - Avoid unnecessary dependencies.
    - Prefer maintainable, boring architecture over clever hacks.

48. PRODUCT NORTH STAR
==========================================================

The CRM must follow this principle:

    ENTER DATA ONCE.
    CONNECT IT TO THE CORRECT ENTITY.
    DERIVE EVERYTHING ELSE AUTOMATICALLY.

Example:

    A machine sale should automatically establish:
        Customer relationship
        Asset record
        Invoice
        Warranty
        Service schedule
        Heatmap entries
        Customer activity
        Analytics data

The user should not have to enter the same information repeatedly.
